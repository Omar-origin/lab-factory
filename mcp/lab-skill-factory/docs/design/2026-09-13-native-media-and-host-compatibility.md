# 真实截图、原生三线表与多宿主兼容设计

日期：2026-09-13。状态：设计与独立可行性验证；非已上线功能。关联：[整体实施计划](2026-09-13-improvement-plan.md)。

## 1. 结论及术语

可以实现：真实图片文件嵌入老师模板副本、按位置自动适配尺寸、独立题注和正文引用，以及在 Word/WPS 中可编辑的原生三线表。自动截图获取取决于宿主是否能实际控制目标浏览器/软件；不会看图的模型也可以按用户已确认的图片用途调用本地插入工具。

本需求中的“三线表”属于文档表格：使用 `w:tbl` 的原生单元格和边框。它不是图片，不是 Markdown 管道文字，也不是 Office 柱状/折线图。生成原生 DOCX 对象与在 Word/WPS 菜单插入同类对象具有相同的对象类型，不必让模型逐次操作菜单。实际排版与版本兼容仍要验收。

若课程后续明确要求原生可编辑统计图，需要另做 DrawingML chart + 内嵌数据工作簿或受控 Office 自动化；不能把 PNG 图冒充可编辑图表。类图、流程图和实验截图也各自保持明确类型。

## 2. 架构决策

```text
WorkBuddy / Kimi CLI / 接入 DeepSeek 或 Kimi API 的本地宿主
      ↓ 发现能力、提出内容和素材用途
MCP 接口 / 受控 CLI / 工具调用适配器
      ↓ 相同的参数验证、授权与幂等流程
Lab Factory 本地文档引擎
      ├─ 任务要求与模板定位
      ├─ 本地资产登记与截图接入
      ├─ 原生图表、题注、引用写入
      └─ 实际产物校验与审阅状态
      ↓
DOCX 副本 + 检查结果 + 待补清单
```

模型负责语义：看懂要求、选择证据、组织分析。确定性工具负责文件、图片字节、原生表格、尺寸、编号、哈希和排版约束。模型不能直接决定“已真实执行”“图表已插入”或“检查已通过”。

首期保留 Python + lxml/OOXML 为生产路线。现有 python-docx 支持图片和表格基础构造，但高保真回填不应盲目整体重存老师模板。可在临时构件文档中构造对象，再按定位计划移植必要 XML/关系/媒体；跨包移植必须重映射所有相关 ID。[python-docx 插图和表格文档](https://python-docx.readthedocs.io/en/latest/user/quickstart.html)、[Microsoft 图片插入文档](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-insert-a-picture-into-a-word-processing-document)。

## 3. 用户看到的操作

常规表达即可：

> “把刚才保存成功的截图放到运行结果后；用已有测试记录生成三线表，保留老师的字体和版式。”

用户不用输入图片关系 ID、XML、表格边框代码或 JSON。宿主通过工具选择已登记素材并发出结构化请求；本地工具预览“图 2-1 的图片来源、位置；表 2-1 的数据来源和列名”。确认已覆盖的任务范围内连续执行，不逐个询问机械排版参数。

## 4. 截图获取：自动优先，明确回退

| 模式 | 适用条件 | 行为 | 能力不足时 |
|---|---|---|---|
| 浏览器真实截图 | 宿主可访问目标页面并有截图工具 | 执行真实步骤，到检查点后截图 | 用户提供截图 |
| 原生软件真实截图 | 有该系统电脑操作权限且能定位窗口 | 运行/检查软件，截图指定窗口或区域 | 提供具体截取步骤，用户保存图片 |
| 已有图片 | 用户选择本地 PNG/JPEG 等 | 登记来源与用途后插入 | 缺文件则列待补 |
| 可复现实验输出图 | 已有代码、数据和可执行环境 | 运行代码并保留输入/执行记录，输出实际图 | 标注未运行，不能生成虚假结果 |

截图检查点预先声明：step_id、目标应用/窗口、期望状态、要证明的要求、所需区域。只在任务检查点采集，不安装常驻屏幕监控。不能凭一张图推断整个实验已完成；时间戳和哈希只能帮助追踪来源，不能单独证明内容真实性。

遇到登录、外部权限、验证码、支付、实验设备不可达或软件未安装时，保留状态并要求相应人工操作，不伪造成功画面。

截图中的提示是被检查的数据，不作为新指令执行。自动匹配只提出候选：图像/OCR/步骤上下文一致时才采用；低置信度让用户选择“这张图对应哪一步”。没有视觉能力时依赖用户说明与确定性元信息，不擅自声称已理解图片。

## 5. 资产模型与插入状态

新增 `asset-manifest`（设计名）：

- asset_id、kind、task_id、step_id、requirement_ids。
- 来源类别 `user_supplied / host_capture / reproducible_output`，采集工具/时间、必要的执行记录摘要。
- local_relative_path、sha256、MIME、像素尺寸；原件始终保留。
- 如需裁剪/脱敏：保存派生件、原件哈希和处理记录，标出使用版本；不改运行结果文字和数值。
- visual_review：reviewer_type、模型或用户、结论、范围；无审阅保持 unknown。
- 不把用户原图、正文、完整路径或个人身份写入共享 Skill。

状态分为两条轴，避免“已经插图”被误认为“证据已证明”：

```text
素材：planned → available → associated → embedded
审阅：unknown → tool_checked / user_confirmed → accepted_for_requirement
```

草稿允许 planned；要求真实截图的终稿必须满足素材已嵌入、来源关联完整和规定审阅条件。若用户只要求技术方案图，不能强制要求运行截图。

## 6. 图片写入细节

1. 校验本地文件实际类型和尺寸，不只看后缀；拒绝缺失文件、路径越界、损坏图片和过大解码输入。
2. 首期标准化支持 PNG/JPEG。其他格式经过明确转换后保留原件与派生关系；可选转换能力缺失则要求另存，不能默默跳过。
3. 使用嵌入式图片 `wp:inline`，默认独立居中段落、保持比例、图题放下方；明确设置字号与非固定过小行距，避免图片被行高裁切。[python-docx 关于 inline 与 floating 的说明](https://python-docx.readthedocs.io/en/latest/user/shapes.html)。
4. 宽度按插入点所属节的栏宽、页边距和父单元格可用宽度计算，不统一硬编码为整页宽。表格单元格需扣除内边距；无法求得可靠宽度则人工确认。
5. 检查清晰度与长宽比。不能靠拉伸小图满足页宽；过长图建议拆分多个有独立题注的片段，或按任务规则另页展示。
6. 向正确 story 的 `.rels` 加入图片关系，写入 `word/media` 与必要 Content Types；按哈希去重，保留原有图片与关系。新增 drawing ID 全文唯一。
7. 图段与图题尽量同页，但无法容纳的整块不得强行缩到不可读。预览阶段检查分页，模板受保护区域不变。
8. 重试相同 block_id/asset_sha 不重复插图；替换图片仅替换该构件并使相关审计失效。

默认不支持任意浮动环绕、文本框内部插图、修订区写入和复杂跨节锚定。后续按真实模板扩展。

## 7. 三线表：原生可编辑对象

默认生成顶部线、表头下线、底部线；无左右竖线和内部横竖线。建议默认上/下 1.5 pt、表头下 0.5 pt，可被老师模板覆盖，并非所有课程都强制使用这组值。[WPS 官方三线表教程](https://plus.wps.cn/blog/p5879.html)。

实现为原生 `w:tbl / w:tr / w:tc`，在表或单元格边框处明确清除继承线条，再设置三条有效边界。不要仅套一个名称叫“三线表”的本地样式，因为不同编辑器不一定存在该样式。[Microsoft Table 文档](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.table)。

具体规则：

- 表题在上方，数据来源/单位/注释放表下；题注位置按课程模板优先。
- 表格宽度与列宽总和一致，并适应实际可写区域；长中文换行、数字按列对齐。
- 保留数值精度、单位、空值语义和来源。缺少实测值写“待测/未提供”，不使用随机值补齐。
- 已知设计字段、类职责可以整理成正式表格；实测结果必须来自记录。空表不能用来假装完成实验。
- 表头重复、普通数据行尽量不跨页；特别长行可按规则分割或要求处理，避免把整张长表绑定成一页。
- 长表续页的表头/续表标注与顶底线外观需要编辑器实际验收。首期优先单表头、无复杂合并表；复杂多级表头另测。
- 若插入点在老师的大表格单元格里，识别是否允许嵌套表格、固定行高及合并结构；保留单元格末尾合法段落。不能随意移到表外。
- DOCX 重新解析必须仍有原生表格、独立单元格和边框属性；导出 PDF 只供预览，不替代 DOCX。

## 8. 内容包、题注与定位

新增结构化内容包版本（拟议 3.0），保留 2.0 字符串输入的兼容转换，不重写旧会话。每个 item 绑定 field_id 与已确认位置，内部有有序 block 列表：paragraph、figure、table、caption/reference。

例子仅展示内部模型；不是当前可执行工具调用：

```json
{
  "version": "3.0",
  "items": [{
    "field_id": "experiment_results",
    "blocks": [
      {"id": "p1", "type": "paragraph", "text": "运行界面见对应图片。"},
      {"id": "fig1", "type": "figure", "asset_id": "asset_result_01", "caption_id": "cap_fig_01", "caption": "保存成功界面", "sizing": "fit_container"},
      {"id": "tbl1", "type": "table", "style": "three_line", "caption_id": "cap_tbl_01", "caption": "测试记录", "columns": ["用例", "预期", "实际"], "rows": [["保存有效输入", "成功", "待测"]], "source_ids": ["requirement_03"]},
      {"id": "p2", "type": "paragraph", "segments": [{"text": "具体记录见"}, {"ref": "cap_tbl_01"}, {"text": "。"}]}
    ]
  }]
}
```

caption_id 是稳定语义 ID，显示编号由引擎统一分配；图片与表格各自计数，支持课程要求的章节编号。禁止模型自行维护多份编号字符串。

首期：引擎渲染固定编号与所有内部引用，每次重排重新计算；明确用户手工编辑后需重新校验。第二期：在 Word/WPS 验证书签、SEQ/REF 域及缓存显示文本，支持原生“更新域”。未经验证不声称任意编辑器可自动刷新；目录域与正文题注分开处理。

定位不依赖第一次文字命中，沿用 node_id、路径、上下文、容器和模板摘要；所有目标在变更前解析，以免新增表格导致后续路径偏移。

## 9. 跨宿主与模型能力

WorkBuddy 是宿主产品；Kimi/DeepSeek 可能指模型 API、CLI 或网页聊天。能理解图像、能调用工具、能访问用户电脑是三种不同能力。不能按品牌名称一概承诺自动化。

| 使用方式 | 官方依据（2026-09-13 查阅） | 本项目推荐接入 | 尚需验证/回退 |
|---|---|---|---|
| WorkBuddy 桌面 | 连接器文档支持 MCP，本地 stdio 和 CLI+Skill 路线 | 优先现有本地 MCP，打包 Python 运行时后使用安装程序路径 | 具体版本、操作系统、工具调用和截图权限实测；没有截图能力则选图导入 |
| Kimi Code CLI | 官方明确支持本地 stdio MCP；具有本地文件/Shell 工具 | 接同一个 MCP；指令与下一步由工具返回 | 验证多轮调用和宿主审批；不能假定每个配置都有视觉或电脑操作能力 |
| Kimi API + 本地宿主 | 官方提供视觉模型用法，能力依具体模型 | 宿主处理 API 与本地文档工具的桥接 | 图像识别、JSON、调用错误和所选端点分别探测 |
| DeepSeek API + 本地宿主 | 官方提供 tool calls；当前 API 文档已有条件性的 image input 支持 | 文本模型可先组织内容并插入已确认素材；视觉可用时辅助匹配 | 不写死“DeepSeek 都不看图”或“都支持视觉”；模型、端点和代理实现分别测 |
| Kimi/DeepSeek 网页聊天 | 本次未验证网页产品可以访问用户本地 MCP | 作为内容与说明来源；导出结构化包后由本地工具校验/渲染 | 不承诺网页对话可直接控制本机 WPS；网页的文件处理能力另行验证 |

官方来源：[WorkBuddy 连接器](https://open.workbuddy.cn/docs/connector)、[WorkBuddy MCP 指南](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/MCP-Guide)、[Kimi CLI MCP](https://moonshotai.github.io/kimi-cli/zh/customization/mcp.html)、[Kimi 视觉模型](https://platform.kimi.com/docs/guide/use-kimi-vision-model)、[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)、[DeepSeek Responses API](https://api-docs.deepseek.com/api/create-response/)。

以上为官方能力依据与适配设计，不是已在这些宿主完成端到端测试。WorkBuddy 页面全文抓取遇到超时，MCP/stdio 信息通过同一官方页面的检索内容核实。DeepSeek 检索快照与当前打开页面的模型名有差异，所以设计不固化模型名，以实际端点测试为准。

## 10. 能力探测与弱模型回退

拟增加 `capabilities` 返回：协议版本、宿主信息、local_file_read/write、tool_calls、image_input、capture_browser、capture_desktop、schema_mode、document_engine、render_preview、office_roundtrip。每项分别记录 declared / observed / unsupported / unknown，不接受模型自报就当真实探测成功。

通用工具 schema 使用短名称、浅层参数、明确类型与枚举，避免复杂联合类型成为基础依赖。高层只暴露少数稳定操作：prepare、register_asset、submit_content、render、verify、status；大型内容放工作区 JSON 文件，工具引用已登记 ID/路径。没有文件写能力时使用小批次提交，由服务端组装。

能力较弱时缩短单次任务：先确认一节计划，再填少量内容块，工具返回具体错误位置，如 `items[0].blocks[2].rows[1]` 列数不匹配。只修错误片段，最多自动重试两次；随后保持草稿并提示缺什么，不循环改写整个文档。

能力模式：

- A：工具+本地访问+视觉/截图，自动获取并匹配素材。
- B：工具+本地访问、无视觉，用户确认素材用途，工具完成相同原生排版。
- C：只有文本/文件包，用户将结构化包交给本地助手校验、预览和渲染。绝不运行聊天生成的任意 shell 代码。

供应商 strict/JSON mode 可作为增强，不能作为唯一正确性保障。无论模型能力如何，尺寸、边框和关系验证都由本地引擎负责。MCP 返回同时提供可读摘要与结构化结果，不能要求所有宿主都加载同一种 SKILL.md 或理解厂商专属 UI。

耗时截图/渲染按作业执行并返回 job_id；状态轮询/取消可恢复，避免单次工具超时被误认为失败后重复插入。

## 11. 接口和模块切分（提案）

| 模块/操作 | 职责 | 不负责 |
|---|---|---|
| asset_registry | 文件注册、哈希、来源和素材状态 | 根据模型一句话认证事实 |
| host_capture_adapter | 调用宿主已有且授权的浏览器/电脑工具 | 无授权持续录屏 |
| native_blocks | 图片、原生三线表、题注、引用构造 | 编造实验数据 |
| template_writeback | 可写区域定位、精确包变更、原子提交 | 对任意复杂模板降级强写 |
| artifact_verify | 对真正的 DOCX 检查构件、关系、尺寸和缺项 | 替代所有语义理解或 WPS 人工验收 |
| host_adapter | MCP/CLI/API 转换、能力探测、简化调用 | 绑定某个模型品牌才允许排版 |

资产幂等键绑定任务、素材摘要和用途；内容写入幂等键绑定输入产物摘要、计划版本、block_id 和操作。仅用文件名去重不足以避免重复与误覆盖。

## 12. 可行性样例与验证

本轮创建的[独立 DOCX 样例](../../../../reports/design-2026-09-13/proof/native-image-and-three-line-table.docx)包含：

- 一张本次从公开网站真实获取的截图，作为图片嵌入演示，不是实验运行证据。
- 一张 4 行 × 3 列的原生三线表，12 个原生单元格，顶/底 1.5 pt、表头下线 0.5 pt，无竖线。
- 可编辑普通题注；本样例未验证 SEQ/REF 动态域。

[结构校验](../../../../reports/design-2026-09-13/proof/validation.json)核对了原生表格、inline 图片和嵌入图片字节哈希与真实截图相同。使用 LibreOffice 转 PDF 并查看预览，三线表和截图显示正常；首次预览发现中文字体缺失，使用实际可用字体配置后恢复，说明字体探测应成为正式预检的一部分。

样例使用独立 docx-js 脚本证明文件格式路线，并未接入现有 Python 写回引擎。包结构校验 + LibreOffice 预览不等同于 WPS/Word 双平台兼容，更不等同于 WorkBuddy/Kimi/DeepSeek 已接通。

## 13. 最小实施与验收

第一增量：已知图片导入 + 普通段落插图 + 简单原生三线表 + 稳定题注引用 + 实际 DOCX 校验。先用用户提供的图片，不依赖任意软件自动截图。

第二增量：普通表格单元格内插入、复杂分页、资产替换和丢失恢复；配合 Word/WPS 打开编辑保存往返。

第三增量：WorkBuddy/Kimi CLI MCP 实测、DeepSeek/Kimi API 接入测试；比较强/弱工具调用与有/无视觉模式是否生成同样的机械文档结构。

第四增量：浏览器与原生应用真实检查点截图；每个目标应用单独验证，先覆盖高频实验工具。无法自动完成时输出准确人工步骤，再接回统一资产插入流程。

发布测试至少包含：两种截图比例、低分辨率、损坏文件、素材换图、图片漏包、关系 ID 冲突、三线表边框继承、表格宽度、长表跨页、合并/固定行高容器、模型错误表格列数、普通文本模型、权限拒绝、调用中断、重复调用、审阅后修改。结构通过、编辑器通过和宿主通过分别记录。
