# DOCX Tooling Policy

## 结论

DOCX 编辑的目标不是“能写进去就行”，而是尽量不破坏老师模板。默认策略是：

1. 先字节级复制原始 `.docx`。
2. 使用 `python-docx` 在副本上做最小范围编辑。
3. 新增内容继承目标锚点附近样式。
4. 无法可靠保真时，停止并输出人工插入提示，不整篇重建文档。

当前推荐默认依赖：

- `python-docx`：默认 DOCX 读取和写入工具。
- `lxml`：辅助处理底层 OOXML，适合检查段落、run、表格、样式、隐藏字段等细节。

不建议在 MVP 默认安装并混用所有工具。每个工具只在合适场景启用。

## python-docx

适合作为跨平台默认 DOCX 编辑层。

适用：

- 查找文本锚点和占位符。
- 在目标段落后插入新段落。
- 填写表格单元格。
- 替换明确占位符。
- 读取并复用目标段落样式、run 字体、字号、粗体、颜色、段落缩进、行距和段前段后。

执行要求：

- 永远先复制原文件，再打开副本编辑。
- `fill-map.json` 必须指定锚点、操作类型和是否保留原文。
- 新增段落默认复制目标段落 `style` 和 `paragraph_format`。
- 新增 run 默认复制目标 run 的字体、字号、颜色、粗体、斜体、下划线等属性。
- 表格填充默认继承目标单元格内原段落样式。
- 不能通过“把整篇文档读成 Markdown 再转回 DOCX”的方式写回。

局限：

- 对复杂封面、文本框、浮动图片、图表、公式、批注、修订、内容控件、自动目录、页眉页脚字段和嵌入对象的保真有限。
- 不能保证 Microsoft Word、WPS、Pages、LibreOffice 渲染完全一致。
- 不能自动更新目录、交叉引用和字段；需要用户或 Word 环境手动刷新。

遇到局限时，保留占位提示，不冒险重建排版。

## docxtpl

`docxtpl` 适合“我们能控制模板”的场景，不适合作为未知老师模板的默认编辑器。

适用：

- 未来我们提供标准模板。
- 用户愿意把老师模板改造成带 Jinja 占位符的模板。
- 同一科目长期复用固定模板，且占位符位置已经稳定。

不适用：

- 用户只给了未知 `.docx` 模板。
- 模板不能被预先加入占位符。
- 第一次草稿要求不改变原结构、原文和排版。

因此 MVP 不默认依赖 `docxtpl`。只有当用户确认“可以改造成受控模板”时，才作为增强方案。

## Mammoth

`Mammoth` 更适合 DOCX 到 HTML/Markdown 的只读抽取，不适合 DOCX 原格式写回。

适用：

- 快速抽取文档文字结构用于理解任务。
- 辅助生成可读预览。

不适用：

- 作为 DOCX 写入工具。
- 往返转换后再覆盖原报告。
- 需要保持字体、字号、分页、表格和复杂版式的场景。

如果使用 Mammoth，只能用于辅助理解，不得用于最终写回。

## pywin32 COM

`pywin32 COM` 可以通过 Microsoft Word 自动化获得更高保真，但它不是跨平台方案。

适用：

- Windows 环境。
- 已安装 Microsoft Word。
- 用户允许调用 Word 自动化。
- 需要刷新目录、字段、页码，或执行 Word 原生另存、排版检查。

不适用：

- macOS 默认环境。
- 未安装 Microsoft Word 的机器。
- 无法接受 GUI/COM 自动化不稳定性的本地工具。

当前 Mac MVP 不依赖 `pywin32 COM`。后续 MCP 可以把它做成 Windows-only 增强 adapter。

## 工具选择顺序

处理 `.docx` 时按这个顺序决策：

1. 默认使用 `python-docx + lxml` 做副本内最小填补。
2. 如果模板是我们可控的占位符模板，才考虑 `docxtpl`。
3. 如果只需要提取文档内容辅助理解，可选 `Mammoth`，但不能写回。
4. 如果运行在 Windows 且有 Word，可选 `pywin32 COM` 做字段刷新和高保真检查。
5. 如果任何工具无法保证保真，输出人工操作提示。

## 安装建议

MVP 阶段：

- 必需：`python-docx`。
- 推荐：`lxml`。
- 暂不默认安装：`docxtpl`、`Mammoth`、`pywin32`。

专属 skill 必须记录当前可用工具。如果 `python-docx` 不可用，只生成 `fill.md + fill-map.json` 和人工插入提示，不直接写 DOCX。
