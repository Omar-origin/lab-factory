# Fill Workflow Policy

## 核心原则

专属 skill 后续写报告时，必须以“填补”为核心。

不要直接改源文件，不要直接生成最终 DOCX，不要删除原文。

DOCX/MD 的格式保真优先级高于自动完成度。无法可靠保真时，输出待办和插入说明，不要冒险重建文档。

DOCX 默认工具策略见 `references/docx-tooling-policy.md`：优先使用 `python-docx + lxml` 在副本上做最小范围填补；不要用 Mammoth 写回 DOCX；不要把 `pywin32 COM` 作为 Mac 默认依赖。

## 第一阶段：fill.md

先生成 `fill.md`，让用户确认新增内容。

生成 `fill.md` 前必须先完成文档理解门禁：

- 从头到尾完整阅读用户当次提供的模板、任务书、评分标准和提交说明。
- 复述实验目标、任务步骤、填写范围、不可触碰区域、工具环境、源码/Notebook、截图来源、提交清单、命名规则和缺失材料。
- 用户确认理解无误后，才生成 `fill.md`。

生成前必须完成模板驱动的需求确认：

- 写作规范：字体、字号、颜色、行间距、标题样式、表格样式、图题/表题、目录和页眉页脚处理。
- 内容粒度：每章写多少、每个小点约多少字、实验小结每栏几点、截图/表格前后是否需要说明。
- 工具环境：必须使用的软件、Notebook、代码环境、系统地址、仓库地址、数据来源和运行方式。
- 提交产物：报告、源码、Notebook、数据集、截图、压缩包格式和文件命名规则。
- 边界：哪些模板区域可填、哪些锁定、截图/绘图/真实数据是否只留占位、finalize 是否再删除提示。

如果用户选择默认，就把 `references/default-writing-parameters.md` 中的具体值当成本次用户要求写入 `fill.md`，不得只写“按默认”。

`fill.md` 包含：

- 文档理解与任务复述。
- 要新增的正文。
- 要新增的表格内容。
- 实验小结。
- 截图/绘图占位提示。
- 工具环境与源码/Notebook 确认。
- 提交清单和命名规则确认。
- 用户待办。
- 写作规范确认摘要。
- 内容粒度确认摘要。

`fill.md` 不包含：

- 删除操作。
- 封面隐私信息长期记录。
- 参考案例原文。
- 未经确认的真实数据。

## 第二阶段：fill-map.json

同时生成 `fill-map.json`，描述每段内容填到哪里。

字段：

- `copy_mode`: 顶层字段，必须是 `byte_for_byte_first`。
- `format_strategy`: 顶层字段，默认是 `inherit_target_anchor`。
- `id`: 稳定 ID。
- `source`: `fill.md` 中的来源位置。
- `target_anchor`: 模板中的文本锚点或占位。
- `operation`: `insert_after`、`replace_placeholder`、`fill_table_cell`。
- `preserve_original`: 默认 true。
- `format_strategy`: item 字段，默认 `inherit_target_anchor`。
- `requires_user_confirmation`: 默认 true。

## 第三阶段：用户确认

用户确认 `fill.md` 后，才允许复制原文件并填入副本。

如果用户指出内容不对，只修改 `fill.md` 和 `fill-map.json`，不要动原文件。

确认前的检查：

- 实验小结默认结构不能少项；若模板包含“问题和解决办法、心得体会、意见与建议”，且用户采用默认，则必须是 3 个问题、3 个心得点、3 个建议点。
- 默认格式不能只停留在说明文字；需要在 `fill.md` 的规则摘要中列出已采用的字体、字号、行距和标题规则。
- 默认正文格式必须列出：小四，中文宋体，英文 Times New Roman，黑色，首行缩进默认度量值 2；除非任务书、模板、评分标准或用户明确要求，不使用其他字体或颜色。
- 默认内容粒度必须区分正文和小结：正文说明点约 150-200 字；实验小结每点约 100 字。
- 所有预览都要邀请用户检查：`请查看，是否存在什么问题？有哪些需要修改的地方？`
- 依赖截图、真实环境或数据的内容必须保留占位，不得编造。
- 如果任务要求 Jupyter Notebook、源码或指定软件，`fill.md` 必须列出源码/Notebook 产物、运行环境、用户需提供或 agent 可生成的部分、截图应来自哪里。
- 如果文档要求压缩包或指定命名，`fill.md` 必须列出最终提交清单和命名模板。

## 第四阶段：复制并填入副本

MCP 复制原文件到输出目录，然后按 `fill-map.json` 执行填补。

复制要求：

- 先做字节级副本，确认副本存在后再打开副本。
- `.docx` 默认用 `python-docx + lxml` 打开副本并按锚点最小范围编辑。
- 不允许通过“读取全文 -> 重新生成 DOCX/MD”的方式替代复制。
- 不允许用 Markdown 转 DOCX 覆盖模板。
- 不允许用 Mammoth 抽取结果再写回覆盖模板。
- `docxtpl` 只有在模板已经是用户确认的受控占位符模板时才允许使用。
- `pywin32 COM` 只有在 Windows + Microsoft Word 环境下作为可选增强；当前 Mac 本地流程不能依赖它。

第一次填入：

- 只新增或填补。
- 不删除。
- 不重排。
- 不覆盖原文。
- 不清理模板说明。
- 不改变原文结构、字体、字号、颜色、分页、目录、表格布局或已有排版。
- 新增段落继承目标锚点段落样式。
- 表格内容继承目标单元格样式。
- 标题、小结、图题、表题优先复用模板已有样式。
- 无法判断样式时，在 `fill.md` 中保留“请用户手动按模板样式粘贴”的提示。
- `python-docx` 无法可靠处理文本框、公式、复杂封面、自动目录、字段或嵌入对象时，停止并提示用户手动处理。

## 第五阶段：工具、源码、截图和绘图

如果实验要求使用指定工具，必须按该工具设计截图和源码流程：

- Jupyter Notebook 类实验：确认 `.ipynb` 文件名、运行环境、依赖、数据集、代码单元、输出图表和指标截图。
- 软件工程系统类实验：确认自选系统、浏览地址、本地或线上环境、GitHub 仓库和需要截图的页面。
- 网络、硬件、仿真、汇编类实验：确认对应软件、命令、仿真文件或运行环境。

截图、绘图、外部软件操作使用真实运行或占位：

```text
【截图：请在 <软件/环境> 中完成 <操作>，截取包含 <关键内容> 的界面】
```

不要生成虚假图片，不要把参考案例图片当成用户图片，不要用生图能力伪造 Notebook、软件界面、浏览器、设备或实验现场截图。

## 第六阶段：Finalize

用户补齐截图/绘图/数据后，进入 finalize。

草稿输出后必须先询问用户是否可以、是否有问题、有哪些地方需要修改。如果用户指出问题，先修正新增内容、占位、`fill.md` 或 `fill-map.json`；如果用户确认草稿没问题且仍需插图/截图/数据，暂停等待用户处理，并提醒用户完成后回来进行第二次修改。

Finalize 前必须确认：

- 截图、绘图、数据是否已经补齐。
- 哪些占位或模板提示要删除。
- 哪些原文要保留。
- 封面个人信息。
- 文件命名方式。

Finalize 必须完成：

- 调整排版，尽量继承模板样式。
- 删除用户确认可删的模板提示、占位和草稿提示。
- 在报告正文最上方放置醒目的免责声明。
- 按用户确认的命名方式输出最终版。
- 最终版经用户确认后，再询问是否要受控迭代专属 skill。
