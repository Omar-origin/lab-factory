# Skill Spec Policy

## 目的

`skill-spec.md` 是专属科目 skill 的生成合同。它让用户先确认规则，再交给 MCP 内置生成器生成真正的 skill；开发环境可用 `skill-creator` 做质量参考，但用户侧不能依赖本机已有 `skill-creator`。

## 必要章节

`skill-spec.md` 必须包含这些章节：

```markdown
# <科目或模板名称> 实验报告 Skill Spec

## 目标
## 适配层级
## 适配范围
## 触发词
## 输入材料
## 文档理解与任务复述
## 需求确认清单
## 需要填写的区域
## 不可触碰的区域
## 写作规范
## 内容粒度要求
## DOCX 工具策略
## 工具环境与提交要求
## 格式保全策略
## 参考案例使用边界
## fill.md 结构
## fill-map.json 规则
## 截图和绘图占位规则
## 草稿流程
## Finalize 流程
## 合规边界
## 版本与迭代
## 验收测试
```

## 需求确认清单

`skill-spec.md` 必须包含需求确认清单，用来证明所有关键规则已经清晰。

每一项必须写明：

- 事项：例如适配层级、填写区域、不可触碰区域、正文格式、标题格式、内容粒度、实验小结点数、必用工具、运行环境、源码/Notebook、截图来源、提交清单、压缩包命名、finalize 边界。
- 采用规则：本次实际执行的具体规则。
- 来源：只能是 `confirmed_by_user`、`default_confirmed` 或 `derived_from_template`。
- 依据：用户回答、模板锚点、任务书条目或默认参数文件中的具体条目。

不允许出现：

- `待确认`。
- `以后再说`。
- `使用默认值` 但没有展开具体默认值。
- `按情况处理` 但没有写清判断规则。

## 适配层级

默认写成科目级或模板系列级 skill。当前实验编号只能作为样例，不应成为唯一触发条件。

如果用户没有明确要求单次实验级，`skill-spec.md` 必须写：

- 默认层级：科目级/模板系列级。
- 当前实验：仅作为初始样例。
- 后续适配：同课程、同模板或同类实验。

只有用户明确确认“一次性，只适配该实验”时，才允许写实验级。

## 文档理解与任务复述

`skill-spec.md` 必须证明已经从头到尾读完整个文档并理解任务，不能只列文件名。

必须包含：

- 已阅读的材料清单。
- 实验目标和核心任务。
- 报告模板结构。
- 需要填写的区域。
- 不可触碰的区域。
- 必用工具、运行环境、源码/Notebook、截图来源。
- 提交清单、压缩包和命名规则。
- 文档中容易漏掉的末尾说明、附录、标红提醒或提交要求。
- 用户已确认的理解摘要。

如果用户还没确认任务理解，不能生成最终版 `skill-spec.md`，只能生成待确认草案并继续询问。

## 需要填写的区域

只能列出明确来自任务书、模板占位或用户确认的区域。

不要写“全文优化”“整体润色”“自动删除无用内容”这类失控规则。

## 不可触碰的区域

必须明确列出：

- 封面原结构。
- 目录。
- 说明页。
- 评分/考核表。
- 教师评语。
- 用户未确认的章节。
- 模板里已有内容。

## 写作规范

必须记录用户确认或默认采用的写作规范：

- 语言：中文、英文或双语。
- 正文字体、字号、颜色、行间距。
- 一级/二级/三级标题字号和样式。
- 图题、表题、编号和说明文字规则。
- 表格样式、页边距、页眉页脚、目录处理。
- 未明确项必须继续追问；用户选择默认后，按 `references/default-writing-parameters.md` 展开具体值，并标注 `来源：default_confirmed`。

如果用户没有提供具体格式规范，使用 `references/default-writing-parameters.md` 的默认值：

- 一级标题：三号，中文宋体，英文 Times New Roman，居中，序号和文字之间一个半角空格，单倍行距，段前 3 行，段后 2 行。
- 二级标题：不缩进，左对齐，小三号，中文宋体，英文 Times New Roman，序号和文字之间一个半角空格，1.5 倍行距，段前 1 行，段后 0.5 行。
- 三级标题：序号缩进两个字符，四号，中文宋体，英文 Times New Roman，序号和文字之间一个半角空格，1.5 倍行距，段前 0.5 行，段后 0 行。
- 正文：小四，中文宋体，英文 Times New Roman，黑色，首行缩进默认度量值 2；不使用其他字体或颜色，除非任务书、模板、评分标准或用户明确要求覆盖。

这些默认值一旦被采用，就不是“备选建议”，而是本次 spec 的强制执行规则。

## 内容粒度要求

必须记录各部分内容的长度和组织方式：

- 实验目的、实验环境、实验步骤、结果分析、实验小结各写多少。
- 实验小结写几点，是否拆成问题与解决、心得体会、意见建议。
- 截图前后是否要写说明。
- 表格是否要补分析。
- 未明确项必须继续追问；用户选择默认后，按 `references/default-writing-parameters.md` 展开具体值，并标注 `来源：default_confirmed`。

如果用户没有提供内容粒度要求，使用默认值：

- 正文中每一个解释说明性质的小点尽量控制在 150-200 字左右。
- 截图、表格、步骤说明等普通说明点默认按 150-200 字左右处理。
- 如果有实验小结，按模板栏目分点写。
- 如果实验小结包含“问题和解决办法、心得体会、意见与建议”，则“问题和解决办法”写 3 个问题，格式为 `问题1：xxx。解决办法：xxx。`；“心得体会”和“意见与建议”各写 3 个小点。
- 实验小结里的每个小点尽量控制在 100 字左右。

这些默认粒度一旦被采用，就必须在后续专属 skill 的 `fill.md` 生成和验收测试中执行。特别是实验小结包含“问题和解决办法、心得体会、意见与建议”时，必须生成 3 个问题、3 个心得点、3 个建议点，不能合并成一段或少写。

## DOCX 工具策略

如果专属 skill 需要处理 `.docx`，必须写明工具策略：

- 默认使用 `python-docx + lxml` 在字节级副本上做最小范围编辑。
- `python-docx` 用于查找锚点、插入段落、填表格单元格、替换明确占位符，并尽量复制目标段落和 run 的样式。
- `docxtpl` 只用于用户确认可改造成受控占位符模板的场景。
- `Mammoth` 只用于辅助抽取内容，不得用于写回或覆盖原 DOCX。
- `pywin32 COM` 只作为 Windows + Microsoft Word 环境下的可选增强，不能作为 Mac 默认方案。
- 无法可靠保真时，输出人工插入提示，不整篇重建文档。

## 工具环境与提交要求

必须记录文档和用户确认中的硬性工具、源码产物、截图来源和提交规则。

至少包含：

- 必须使用的工具、平台或环境，例如 Jupyter Notebook、Python、MATLAB、Logisim、Packet Tracer、DOSBox、浏览器、本地系统地址、GitHub 仓库。
- 是否需要 agent 帮用户生成、修改或整理源码/Notebook；如果需要，源码产物名称、路径、依赖、数据和运行方式是什么。
- 是否需要真实运行截图、Notebook 截图、软件截图、系统浏览截图、图表或结果截图；截图来源必须是真实运行、用户提供材料或可复现代码输出。
- 提交文件清单，例如实验报告、`ex6.ipynb`、源码目录、数据集、压缩包。
- 压缩包格式和命名规则，例如 `.rar`、`.zip` 以及姓名、学号、班级、序号等占位字段。
- 哪些个人信息可以后置到 finalize 前询问，且不得写入专属 skill。

如果文档写明 `实验报告及源代码（ex6.ipynb）提交要求`，则不能只生成报告 skill；必须把 Notebook/source 产物、截图来源、压缩包命名和最终提交清单写入 spec。

如果工具或环境未明确，但任务显然依赖工具执行，必须追问用户，不能默认跳过。用户尚未提供工具、源码或截图时，专属 skill 应输出可执行步骤和占位，不编造运行结果。

## 格式保全策略

必须明确：

- 原文件只读，先做字节级副本，再修改副本。
- DOCX 不允许整篇重建、另存为新模板、Markdown 转 DOCX 覆盖原文档。
- 新增内容默认继承目标锚点所在段落或表格单元格的样式。
- 无法可靠继承格式时，停止并提示用户，而不是冒险破坏排版。
- 第一次草稿只填补，不删除、不重排、不覆盖原文。
- 文档原本结构、字体、字号、颜色、段落、分页、目录、表格布局和已有内容默认全部锁定。
- 任何会改变原文结构或样式的操作必须后置到 finalize，并且只在用户明确确认范围后执行。

## fill.md 结构

`fill.md` 是用户确认用的内容预览。它只写要填补的新增内容，不写入删除操作。

`fill.md` 必须包含本次采用规则摘要：

- 写作规范确认：列出字体、字号、行距、标题样式、表格/图题规则，注明来源。
- 内容粒度确认：列出每部分段落数、每点字数、实验小结每栏点数，注明来源。
- 工具环境与提交确认：列出必用工具、源码/Notebook、截图来源、提交清单和命名规则，注明来源。

每段内容都要有稳定 ID，例如：

```markdown
<!-- fill-id: experiment.summary.problem_1 -->
### 问题一：...
```

## fill-map.json 规则

每个 fill item 都要映射到模板锚点：

```json
{
  "copy_mode": "byte_for_byte_first",
  "format_strategy": "inherit_target_anchor",
  "items": [
    {
      "id": "experiment.summary",
      "source": "fill.md#experiment.summary",
      "target_anchor": "实验小结（包括问题和解决办法、心得体会、意见与建议等）",
      "operation": "insert_after",
      "preserve_original": true,
      "format_strategy": "inherit_target_anchor"
    }
  ]
}
```

## 验收测试

至少包含：

- 不直接生成最终报告。
- 生成 skill-spec 前从头到尾完整理解文档，并复述任务要求让用户确认。
- 能生成 `fill.md`。
- 能生成 `fill-map.json`。
- 草稿阶段保留原文。
- 默认生成科目级/模板系列级 skill，不把实验编号圈死为唯一范围。
- 生成前根据模板多轮确认写作规范和内容粒度，直到每项规则清晰。
- 用户选择默认时，能把内置默认参数展开为具体执行规则，并当成本次用户要求执行。
- DOCX 草稿保持原模板排版，不能整篇重建。
- 文档原本结构、字体、字号、内容、格式和排版默认不被修改。
- DOCX 工具策略正确：默认 `python-docx + lxml`，不把 Mammoth 当写回工具，不把 pywin32 当 Mac 默认依赖。
- 生成前完整浏览模板/任务书，包括文末提交说明、命名规则和源码提交要求。
- 能识别并追问必用工具、运行环境、源码/Notebook、系统地址和提交产物。
- 截图/绘图只来自真实运行、用户材料或可复现代码输出；不能用生图伪造截图。
- 参考案例不被复制。
- 草稿后询问用户是否满意或有问题；没问题时等待用户补齐截图/绘图/数据后再二次修改。
- finalize 前确认删除项、封面信息和文件命名方式，并在最终版末尾添加免责声明。
- 正文默认首行缩进度量值 2；正文默认说明点约 150-200 字；实验小结默认结构能生成 3 个问题、3 个心得点、3 个建议点，每点约 100 字。
