# Tool And Artifact Policy

## 目标

有些实验报告不是纯文档任务，而是“工具运行 + 源码/Notebook + 截图/结果 + 报告 + 打包提交”的组合任务。专属 skill 生成前必须把这些要求问清楚并写进 `skill-spec.md`。

## 完整浏览要求

在提问前，先完整浏览用户已经提供的模板、任务书、评分标准和提交说明。重点不能只看标题和正文开头，还要检查：

- 文档最后几页、最后若干段、附录、备注和老师提醒。
- “提交要求”“命名规则”“压缩包”“源代码”“附件”“标红部分自行修改”等段落。
- 文件名模板，例如 `实验六—聚类算法应用与结果评估-软件24-00x班-学号-姓名.rar`。
- 需要同时提交的文件，例如实验报告、`ex6.ipynb`、源码文件、数据集、截图或压缩包。
- 必须使用的工具、平台或环境，例如 Jupyter Notebook、Python、MATLAB、Logisim、Packet Tracer、DOSBox、浏览器、本地系统地址、GitHub 仓库。

如果脚本输出被截断，必须另外查看文档尾部和关键词命中的段落，不能因为摘要里没有出现就认为没有提交要求。

## 必须确认的问题

浏览后再用口语化问题确认，不要直接抛术语。常见问法：

- “我看到文档里提到要交 `ex6.ipynb`，这次是要我帮你一起整理 Notebook 代码，还是你已经有源代码文件？”
- “老师要求用 Jupyter Notebook 吗？你是在本机 Jupyter、Anaconda、VS Code 还是其他环境里跑？”
- “这个实验需要真实运行截图。你希望我先写可运行代码和截图提示，还是你已经有运行结果和截图？”
- “软件工程这个实验里自选的系统是什么？能给我本地地址、GitHub 地址或浏览器访问地址吗？如果没有，我就只能留占位提示。”
- “文档末尾有压缩包命名规则。姓名、学号、班级这些信息可以等最终版前再填，你现在要不要先确认命名模板？”

每个必用工具、源码产物和提交文件都必须有来源：

- `derived_from_template`：文档或任务书明确写了。
- `confirmed_by_user`：用户补充确认。
- `default_confirmed`：只有文档没有要求且用户选择默认时才使用。

## 源码和 Notebook 规则

如果实验要求提交源码、Notebook 或工程文件，专属 skill 不能只写报告正文。必须在 `skill-spec.md` 和 `fill.md` 里记录：

- 需要生成、修改或引用的源码产物名称，例如 `ex6.ipynb`。
- 代码运行环境、依赖、数据输入和输出结果。
- 是否由 agent 帮用户创建/补充代码，还是只引用用户已有代码。
- 需要插入报告的代码截图、运行截图、图表或结果截图。
- 如果当前环境无法运行，保留可执行步骤和截图提示，不编造运行结果。

生成代码或 Notebook 时，源码产物必须作为独立文件或独立待办处理，不得把完整源码长期沉淀进专属 skill。

## 截图和图片规则

- 不使用生图能力生成老师要求的运行截图、界面截图、Notebook 截图、软件截图、设备照片或实验现场照片。
- 可以根据真实数据和真实代码生成图表，但必须说明图表来源于可复现代码或用户数据。
- 如果没有真实运行环境、真实截图或可复现数据，使用占位提示，例如：

```text
【截图：请在 Jupyter Notebook 中运行 ex6.ipynb 的聚类代码，截取包含代码单元、输出图表和评价指标的界面】
```

## 提交和打包规则

如果文档要求提交压缩包、源码、Notebook 或指定命名，专属 skill 必须输出提交清单：

- 最终报告文件。
- 源码、Notebook、数据集或工程文件。
- 压缩包格式，例如 `.rar` 或 `.zip`。
- 命名模板和需要用户填写的字段。
- 哪些字段可后置到 finalize，例如姓名、学号、班级、序号。

Finalize 前必须再次确认命名和提交清单，避免只生成报告却漏交源码或压缩包。
