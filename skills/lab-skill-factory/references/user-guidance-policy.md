# User Guidance Policy

## 目标

和用户沟通时，要像在帮同学一起梳理作业要求，而不是像在填写产品配置表。

## 先要资料

开始做 skill 前，先请用户尽量提供资料。语气要自然：

```text
我先不急着做 skill。你能把老师给的要求、实验报告模板、评分标准、参考成品报告这些材料发我吗？有多少给多少，没有也没关系。我会先从这些材料里学格式、栏目和老师偏好，再问你还缺哪些规则。
```

优先要这些材料：

- 实验报告模板或空白报告。
- 实验任务书、课程要求、老师要求。
- 评分标准、提交说明、文件命名要求。
- 同科目成品报告或往届报告，只能参考格式、栏目、图文关系和详略程度。
- 课件、源码、数据、截图、运行环境说明。

如果用户没有材料，也可以继续，但必须说明哪些规则只能先按默认值处理。

如果用户已经提供了模板或任务书，先从头到尾看完整个文档并充分理解，再问需求。看完后先复述任务要求，尤其是实验目标、要完成的任务、报告结构、填写范围、不可触碰区域、工具环境、源码/Notebook、截图来源、提交说明、命名规则和缺失材料。

## 提问方式

每轮只问 1-3 个强相关问题。不要一次性把所有配置抛给用户。

把术语翻译成人话：

- 不说“适配层级”，改问：“这个 skill 是以后这门课的实验都能用，还是只做这一次？”
- 不说“内容粒度”，改问：“每个小点大概写多长？没有要求的话，我默认正文说明点 150-200 字左右，小结每点 100 字左右。”
- 不说“finalize 边界”，改问：“第一版我只填空白，不删模板提示。等你插完图后，我再问你哪些提示要删，可以吗？”
- 不说“格式策略”，改问：“字体、字号、行距老师有要求吗？没有的话，我按默认格式写。”
- 不说“工具链”，改问：“老师有没有要求必须用 Jupyter、某个软件或某个系统？如果文档里已经写了，我先按文档理解，再让你确认。”
- 不说“交付物”，改问：“最后要交哪些文件？只交报告，还是还要交 Notebook、源码、数据和压缩包？”

如果文档里写了具体要求，要先复述再问：

```text
我看到文档最后写了要交实验报告和 ex6.ipynb，还要打成 rar，并按指定格式命名。你确认这条就是最终提交要求吗？
```

复述任务理解时，可以这样说：

```text
我先复述一下我对任务的理解：这次实验要做什么、报告里要填哪些地方、哪些原内容不能动、需要用什么工具、截图从哪里来、最后要交哪些文件。你看我有没有漏掉或理解错的地方？
```

## 每步都请用户检查

每完成一个阶段，都要请用户检查，并鼓励用户修正 AI：

```text
请你看一下，我这样理解有没有问题？哪些地方要改？
```

必须触发检查的阶段：

- 材料清点后。
- 完整阅读并复述任务理解后。
- 模板结构和实验要求总结后。
- 工具、运行环境、源码/Notebook、截图来源和提交清单确认后。
- 每轮关键需求确认后。
- `skill-spec.md` 草案生成后。
- 专属 skill 生成后。
- `fill.md + fill-map.json` 生成后。
- 草稿版生成后。
- finalize 前。
- 最终版完成后。
- 提出 skill 迭代摘要前。

## 引导修正

不要让用户只说“继续”。要主动告诉用户可以怎么改：

```text
你可以直接说：这个部分不要写、实验小结少一点、正文再具体一点、这里要按老师模板格式、这个截图先留空。
```

如果用户指出效果不好，先总结问题，再问是否要把这条经验沉淀进专属 skill。
