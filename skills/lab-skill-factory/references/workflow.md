# Workflow

## 1. 接收材料路径

用户可能只说：

```text
帮我完成这个实验报告：<路径>
```

不要直接写报告。先清点并完整浏览用户已经给出的材料，判断用户真正需要的是：为这个科目/模板定制实验报告专属 skill。

如果用户已经给了模板、任务书或材料路径，第一动作不是提问，而是只读浏览这些材料。浏览后再用通俗话请用户补充缺失材料。不要直接问一堆配置，问法可以是：

```text
我先看完你已经给的模板/任务书，再做 skill。看完后我会告诉你我从文档里读到了哪些要求，尤其是工具、截图、提交文件和命名规则。你还可以补充这些材料，有多少给多少，没有也没关系：
1. 实验报告模板或空白报告
2. 实验任务书/课程要求/老师发的要求
3. 评分标准或提交说明
4. 同科目以前写好的成品报告，只用来看格式和详略，不抄内容
5. 课件、源码、数据、截图或运行环境说明
```

如果用户没有这些材料，可以继续，但必须在需求确认清单里记录“缺少哪些材料”，并把对应规则标成用户确认或默认确认，不能假装已经从材料中学到。

材料清点和完整理解后必须停下来请用户检查：

```text
请查看，我目前从材料里读到的要求和缺少的材料有没有问题？尤其是工具环境、源码/Notebook、截图、提交文件和命名规则，有没有老师另外说过但文档里没写的？
```

材料可能包括：

- 实验报告模板。
- 实验任务书或实验要求。
- 同科目参考案例。
- 历史报告。
- 课件、评分标准、源码、数据、截图。
- 用户补充的写作偏好、文件命名规则、封面信息。

## 2. 完整只读分析与理解复述

先完整只读分析材料。不能只看标题、前几页、前 200 个段落、关键词命中段落或脚本摘要；必须从头到尾阅读文档，检查文档末尾、附录、备注、标红提醒和提交说明。

- 实验目的。
- 实验类型，例如代码类、网络命令类、软件工程文档类、硬件/仿真类、数据分析类。
- 模板结构、章节、表格、占位、截图位置。
- 需要填写区域。
- 不可触碰区域，例如封面、目录、说明页、考核表、已有正文。
- 已有格式信号，例如字体、字号、标题层级、行间距、表格样式、编号、页眉页脚、目录、封面控件。
- 必须使用的工具、平台、软件、运行环境或系统地址，例如 Jupyter Notebook、Python、MATLAB、Logisim、Packet Tracer、DOSBox、本地浏览器地址或 GitHub 仓库。
- 需要用户补充的源码、Notebook、截图、绘图、真实数据或个人操作。
- 需要同时提交的文件，例如报告、`ex6.ipynb`、源码目录、数据集、压缩包。
- 文档末尾的提交要求、压缩包格式、文件命名模板、标红字段和个人信息占位。
- 可从模板推断的标题级别和内容粒度，例如实验小结是否存在、是否要求问题/心得/建议分点。

可以运行 `scripts/inspect_lab_materials.py` 和 `scripts/extract_docx_outline.py` 辅助分析。

`extract_docx_outline.py` 的 `paragraphs` 会按顺序输出完整段落；必须从头到尾阅读，同时查看 `paragraphs_tail` 和 `requirement_paragraphs`。如果材料是 PDF 或旧 `.doc`，也必须确认最后几页或最后段落是否包含提交说明。

分析完成后，必须输出“我对任务的理解”，证明已经充分理解文档。复述至少覆盖实验目标、具体任务、报告结构、填写范围、不可触碰区域、工具环境、源码/Notebook、截图来源、提交清单、命名规则和缺失材料。

建议格式：

```text
我对任务的理解：
1. 实验目标：
2. 需要完成的任务：
3. 报告里需要填写的区域：
4. 不能动的原文区域：
5. 必须使用的工具/环境：
6. 需要的源码/Notebook/数据：
7. 截图和图表来源：
8. 写作和格式要求：
9. 提交清单和命名规则：
10. 目前还缺的材料或需要你确认的点：

请查看，我这样理解是否准确？有没有漏掉或误解的要求？
```

如果用户指出理解有误，必须先修正复述，再进入多轮确认或生成 `skill-spec.md`。不能在任务理解未确认时生成专属 skill。

例如：

```text
我先读到这些硬性要求：需要用 Jupyter Notebook；需要提交实验报告和 ex6.ipynb；压缩包命名是“实验六—聚类算法应用与结果评估-软件24-00x班-学号-姓名.rar”；截图必须来自 Notebook 运行结果。你看这些有没有漏？
```

## 3. 模板驱动的多轮确认

按模板和任务书逐项确认需求。不要一次性抛出全部问题；每轮只问 1-3 个强相关问题。上一轮回答仍不足以落成规则时，必须继续追问，直到每一项都有明确来源。

提问必须口语化。避免把内部术语直接抛给用户：

- 不要问：“请确认适配层级。”
- 改成问：“这个 skill 是以后这门课的实验都能用，还是只服务这一次实验？”
- 不要问：“请确认内容粒度。”
- 改成问：“每个小点大概写多长？如果你没要求，我默认正文说明点写 150-200 字左右，小结每点写 100 字左右。”
- 不要问：“请确认 finalize 边界。”
- 改成问：“第一版我只往空白处填内容，不删模板提示。等你插完图之后，我再问你哪些提示要删，可以吗？”
- 不要问：“请确认工具链和交付物。”
- 改成问：“文档里提到要用 Jupyter/某个软件/某个系统的话，你是要我帮你整理代码和运行步骤，还是你已经有源码和截图？”

每轮问完后，必须给用户一个简短理解摘要，并主动邀请用户纠正：

```text
我先按这个理解：这门课通用；第一版只填空白处；格式没特殊要求就用默认；小结按三栏三点写。你看哪里不对，直接改我。
```

所有阶段都要有检查点。每次产出摘要、草案、预览、草稿或迭代建议后，都要用类似这句话收尾：

```text
请查看，是否存在什么问题？有哪些需要修改的地方？
```

每项需求必须标记来源：

- `confirmed_by_user`：用户明确提供。
- `default_confirmed`：用户选择默认，已把内置默认值展开为本次要求。
- `derived_from_template`：模板、任务书或评分标准明确规定。

禁止把“待确认”“以后再说”“使用默认值”直接写进 `skill-spec.md`。如果用户选择默认，必须展开为具体值，例如字号、字体、行间距、实验小结每栏几点、每点约多少字。

默认适配层级：

- 默认做“科目级/模板系列级”专属 skill，让它适配该课程或同一模板体系下的多个实验。
- 不要因为当前样例是“实验八”就生成“只适配实验八”的 skill。
- 只有用户明确说“只做这一次实验”“只适配实验八”时，才生成实验级 skill。
- 如果材料标题只有实验编号，先从课程名、文件夹名、封面或任务书推断科目名；无法推断时再问用户。

按顺序优先确认：

- 这个专属 skill 的适配层级：默认科目级/模板系列级，是否需要改成单次实验级。
- 科目/课程/模板系列名称，以及当前实验编号只作为样例还是固定范围。
- 需要填写哪些区域。
- 哪些区域绝对不能动。
- 文档或老师是否要求必须使用某个工具、环境、Notebook、源码文件、系统、网站或仓库；如果文档已经写明，先复述再让用户确认。
- 如果是代码类实验，是否要生成或整理源码/Notebook，源码文件名是什么，是否需要真实运行，数据和依赖在哪里。
- 如果是系统类实验，用户自选的系统是什么，浏览地址是本地、线上地址还是 GitHub 仓库，是否需要用户提供可访问链接或截图。
- 写作规范是否有明确要求：中文/英文、字体、字号、标题字号、行间距、段前段后、表格样式、图题/表题、编号规则、颜色要求、页边距。必须在浏览模板和任务书后再问；用户选择默认时，把 `references/default-writing-parameters.md` 中对应默认值逐项写入本次规则。
- 内容粒度要求：各章节大约写多少、实验小结写几点、问题分析/心得/建议是否分点、每张图前后是否要解释、表格是否要补说明。必须结合当前模板具体分析后再问；用户选择默认时，采用并展开默认粒度：正文解释说明小点约 150-200 字；实验小结按模板栏目分点；若包含“问题和解决办法、心得体会、意见与建议”，则每栏 3 小点，每点约 100 字。
- 是否有同科目参考案例，且只作为格式参考。
- 截图、绘图和图片的来源：真实运行截图、用户已有截图、可复现代码图表，还是只能留占位；禁止把老师要求的真实截图交给生图能力处理。
- 提交清单和命名规则：是否要交报告、源码、Notebook、数据集、压缩包；压缩包格式和命名模板是什么。
- 是否需要在 finalize 时填写封面和命名。

个人信息和具体文件命名可以后置到 finalize 阶段，不必在生成 skill 时保存。

### 3.1 必须问清的模板问题

生成 spec 前至少确认这些问题，模板已明确时可记录模板来源：

- 哪些章节只保留模板原文，哪些章节允许新增内容。
- 占位文字是第一版保留，还是 finalize 时确认后删除。
- 封面、目录、成绩表、教师评语是否锁定。
- 正文、标题、表格、图题、截图占位分别继承模板样式还是采用默认样式。
- 每个正文小点的长度、段落数或表格行数。
- 实验小结是否按“问题和解决办法、心得体会、意见与建议”三栏写；每栏写几点。
- 是否需要真实截图、运行结果、源码、Notebook、数据或环境信息；未提供时是否先帮用户生成可运行代码/Notebook 草案，还是只留占位和操作步骤。
- 是否存在文末提交要求、压缩包命名要求、源码文件名要求；如果有，逐条写入 spec。
- 后续同科目实验是否复用同一规则。

### 3.2 默认值即用户要求

当用户回答“默认”“按默认”“都默认”“你定”或同等意思时：

- 立即把默认值展开成具体规则，不再把该项视为待确认。
- 在 `skill-spec.md` 中标注 `来源：default_confirmed`。
- 在专属 skill 的 `references/default-writing-parameters.md` 中保留默认值，并在 workflow/fill-policy 中要求执行这些值。
- 后续生成 `fill.md` 时，在“写作规范确认”和“内容粒度确认”中列出本次采用的默认规则。

## 4. 生成 skill-spec.md

先生成 `skill-spec.md`，不要直接写 `SKILL.md`。

`skill-spec.md` 是用户确认专属 skill 规则的合同。它必须说明：

- 触发词。
- 适配层级。
- 适配范围。
- 输入材料。
- 文档理解与任务复述。
- 可填写区域。
- 不可触碰区域。
- 写作规范。
- 内容粒度要求。
- 工具环境、源码/Notebook、截图来源、提交清单和命名规则。
- 内置默认参数及其被覆盖条件。
- 格式保全策略。
- DOCX 工具策略。
- `fill.md` 结构。
- `fill-map.json` 规则。
- 截图/绘图占位规则。
- 草稿与 finalize 两遍流程。
- 合规边界。
- 版本和迭代策略。

用户确认前，不要生成专属 skill 文件。

## 5. 生成专属 skill

用户确认 `skill-spec.md` 后，生成专属 skill。

开发环境可以调用 `skill-creator` 做质量参考；商业分发给用户时，不能依赖用户电脑已有 `skill-creator`，必须使用 MCP 内置模板、校验器和脚手架生成器兜底。

执行时应把 `skill-spec.md` 作为输入，生成：

```text
skills/<subject-skill-slug>/
  SKILL.md
  references/
    workflow.md
    document-understanding-policy.md
    docx-tooling-policy.md
    fill-policy.md
    finalize-policy.md
    formatting-notes.md
    tool-artifact-policy.md
    user-guidance-policy.md
    default-writing-parameters.md
    compliance.md
    iteration-log.md
  assets/
    fill-template.md
    fill-map.schema.json
  evals/
    evals.json
```

专属 skill 的职责是后续生成 `fill.md + fill-map.json` 和必要的辅助产物计划，不是直接改源文件。

## 6. 专属 skill 执行报告流程

专属 skill 后续固定执行：

1. 从头到尾完整阅读用户当次提供的模板、任务书和材料。
2. 复述任务要求和缺失材料，等待用户确认理解无误。
3. 根据用户材料生成 `fill.md`。
4. 同时生成 `fill-map.json`，标明每段内容填入哪个锚点，并声明格式继承策略。
5. 用户确认 `fill.md`。
6. MCP 对原文件做字节级副本。
7. MCP 按 `fill-map.json` 填入副本，新增内容继承目标锚点附近样式。
8. 输出草稿。
9. 草稿输出后立即询问用户：`请查看，草稿是否可以？是否存在什么问题？有哪些需要修改的地方？`
10. 如果用户指出问题，先修改 `fill.md`、`fill-map.json` 或草稿副本中的新增内容，再次请用户检查。
11. 如果用户确认草稿没问题，但仍有截图、绘图、真实数据或手工操作未完成，暂停等待用户处理，并提醒：`你补完图片/截图/数据后，再回来告诉我，我会做第二次修改。`
12. 用户完成截图/绘图/数据后，进入第二次 finalize：调整排版，删除用户确认可删的模板提示、占位和草稿提示，在报告最后添加免责声明，并询问文件命名方式。
13. 按用户确认的命名方式输出最终版。
14. 用户确认最终版后，再询问是否要受控迭代专属 skill。

## 7. 受控迭代

完成一次报告后：

1. 请用户检查最终报告：是否有不满意、写错、格式不对、字数不够、截图缺失或流程卡住的地方。
2. 询问是否要更新迭代专属 skill。
3. 如果用户愿意更新，先总结本次流程里值得沉淀的方向，例如格式修正、锚点修正、小结结构、截图占位、默认字数、finalize 删除规则。
4. 输出“拟更新摘要”，明确哪些是通用规则，哪些只是本次特殊情况不应泛化。
5. 用户确认后，MCP 写入新版本。
6. 更新 `CHANGELOG.md` 或 `iteration-log.md`。
7. 保留旧版本可回滚。
