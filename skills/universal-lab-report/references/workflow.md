# Workflow

## 1. 材料清点

读取用户给出的全部路径。路径可以是文件、目录、标准输入文件夹或混合输入。先完整清点材料，不要急着写报告。

必须识别这些角色：

- 实验任务书或实验要求。
- 实验报告模板。
- 成品实验报告样例。
- 实验所需文件，例如源码、项目、数据集、SQL、日志、模型、Notebook、网页。
- 实验相关课件、教材、PPT、PDF。
- 原始数据、截图、运行记录、测量记录。
- 个人信息、评分标准、输出要求、目标写作风格。

如果材料足以判断实验主题，也不要立刻写报告。先创建输出工作区并在副本里查看文档。

## 2. 创建输出工作区

在源材料旁边创建输出工作区，默认命名：

```text
实验报告助手输出/<实验名或任务名>-<时间戳>/
```

工作区建议包含：

```text
source-copy/
artifacts/
draft/
final/
notes/
```

先把全部源材料复制到 `source-copy/`，后续只处理副本。不要改原始路径里的文件。

## 3. 查看文档并提取实验要求

在 `source-copy/` 中查看任务书、报告模板、已有报告、评分标准和输出要求。无论用户是否提供参考案例，都必须先明确：

- 实验标题、课程或实验编号。
- 实验目的、原理、环境、工具和数据。
- 必做步骤、截图要求、表格要求、公式要求、代码或命令要求。
- 分析、实验小结、心得、问题和建议。
- 提交格式、命名规则、页数或字数要求。
- 评分标准映射，如果提供了 rubric。

同时识别需要使用的环境和工具，例如：

- 操作系统、编程语言、IDE、Notebook、数据库、浏览器、网络工具、仿真软件、建模软件、硬件平台。
- 数据文件、源码入口、运行命令、账号或远程环境需求。
- 需要用户手动完成的外部软件、课堂环境、设备或截图步骤。

形成一份内部章节清单和工具环境清单。写作前必须确认每个任务要求会被正文、占位、用户待办或缺失说明覆盖。

## 4. 需求澄清与填写范围确认

在写草稿前，先按 `interaction-policy.md` 向用户确认关键需求。问题要一问一答，不要一次性列出一大堆让用户同时回答。能从模板或任务书明确看出的内容不要重复问；看不出的内容按默认要求处理或延后。

需要逐步明确或记录默认值的项目：

- 报告语言：中文、英文、中英混排。
- 标题格式：字体、字号、颜色、加粗、编号层级。
- 正文格式：字体、字号、颜色、行间距、段前段后、首行缩进。
- 表格格式：表头、边框、字体、编号、是否需要三线表。
- 图片格式：图片位置、图注格式、图文关系、是否一段文字配一张图。
- 代码和命令格式：是否保留代码块、是否删除运行命令、是否截图展示。
- 实验小结要求：问题与解决办法、心得体会、意见建议的数量和字数。
- 输出要求：草稿版、最终版、命名规则、输出位置。

如果用户没有提出某项要求，记录为“使用内置默认要求”。内置默认表先留空，待后续补充，不要临时发明一套无法追踪的默认值。个人信息、详细软件版本、最终文件名等可以先不问，等 finalize 或必须使用时再问。

必须向用户确认填写范围：

- 列出根据任务书、模板占位和报告结构判断需要填写的章节、表格、图片位置、封面字段或小结区域。
- 列出不可触碰范围：没有被任务书要求、模板占位标明或用户确认的地方，只能保留原样。
- 如果某处是否需要填写不确定，先问用户；不要自行改动。

必须向用户确认环境和工具：

- 先列出从文档中识别出的环境/工具需求。
- 默认记录为“本机执行/本机环境待确认”。
- 只有运行、截图、正文环境描述或结果解释必须依赖具体环境时，才询问用户实际使用哪些软件、版本、平台、数据文件、源码目录或运行环境。
- 如果用户指定了环境工具，后续运行、截图、分析文字和操作指导都按用户确认的环境工具写。
- 如果用户没有这些环境工具，使用占位引导或替代说明，不要假装用户使用过。

同时询问用户是否有同科目参考案例。参考案例不要求是同一个实验，主要用于学习：

- 报告排版和章节组织。
- 每个栏目通常填写什么。
- 文字与图片的对应关系。
- 图注、表格、代码、截图的摆放习惯。
- 老师偏好的详略程度。

参考案例不得作为改写底稿，不复制正文、数据、截图、个人信息或独特表达。

## 5. 确定格式和模板策略

有模板时：

- 模板控制封面字段、标题层级、表格样式、图注位置、页面结构和默认格式。
- 尽量在模板副本上插入或替换内容，不从零生成一个完全不同的文档。
- 草稿阶段保留模板和原报告里的所有原有内容，包括“可删除”“填写后删除”“此处填写”等提示文字。不要在草稿阶段删除它们。
- 无法保持的复杂格式要在交付说明里列出风险。

写草稿前按 `template-editing-policy.md` 建立模板地图：

- 段落、表格、占位、章节锚点。
- 哪些内容在表格中，哪些在表格外。
- 每个要填写内容对应哪个锚点。
- 哪些原文必须保留。

没有锚点的内容不要写。先询问用户或放入待办。

没有模板时：

- DOCX 默认结构：封面、实验目的、实验原理、实验环境、实验步骤、实验结果与分析、实验小结、免责声明。
- Markdown 默认使用清晰标题、表格、代码块和占位提示。

## 6. 确定证据模式

按 `evidence-policy.md` 选择真实数据、参考示例、占位引导或混合模式。

默认是占位引导模式。用户提供数据、截图、日志或可运行文件时优先使用真实材料。用户明确要求参考示例时，正文也要标注参考性质。

## 7. 处理截图和不可自动完成项

按 `screenshot-policy.md` 检查是否能从已有材料或本地可复现结果得到截图。

无法复现或不应伪造的项目，留下具体提示：

```text
【截图：请在 XXX 软件中打开 XXX 页面，截取包含 XXX 的完整界面】
```

同时在用户待办清单中列出操作步骤。

## 8. 生成草稿版

草稿版只填写用户确认的填写范围。它应覆盖任务书要求，并允许保留：

- 截图占位。
- 个人信息占位。
- 待用户实测数据占位。
- 参考示例标注。
- 用户操作说明。
- 缺失项清单。

草稿版不得删除任何原始内容。新增内容应插入到合适位置，或在占位附近补充；如果原有提示文字显然最终应删除，也先保留，并在交付说明中列成“待用户确认删除项”。

没有被用户确认需要填写的地方，保持原样，不做“顺手优化”、不改写、不调换位置。

DOCX 草稿必须遵守：

- 不从零重建文档。
- 不把整篇报告写入一个大表格单元格。
- 不新建重复的“实验小结”标题。
- 如果已有“实验小结（包括问题和解决办法、心得体会、意见与建议等）”，就在该锚点后插入小结正文。
- 目录页、说明页、文档变更历史、考核表必须保留。

草稿版也要附免责声明，因为用户可能直接查看或转用。

草稿生成后，如果是 DOCX，运行或等价执行原文保全检查，确认源模板关键文本仍在草稿中。发现目录、说明页、实验小结锚点或考核表缺失时，先修复草稿，不要交付。

## 9. 用户补齐后确认删除项、封面信息并 finalize

用户补充截图、数据、个人信息或确认可提交后，按 `finalize-policy.md` 生成最终版。

执行 finalize 前必须询问用户是否有内容需要删除，尤其是：

- 模板原有的“可删除”“填写后删除”“此处填写”等提示。
- 草稿阶段留下的截图提示、用户待办、参考说明。
- 用户认为不应出现在最终版里的原文。

只有用户确认删除范围后，才删除对应内容并调整排版。最终版要保留规范正文、图片、表格、图注、必要说明和免责声明。

如果报告有封面或文件名要求，finalize 前必须：

- 根据封面页字段识别需要填写的个人信息，例如姓名、学号、班级、课程名、指导教师、日期、小组成员。
- 向用户询问缺失信息，不要从其他材料中猜测隐私字段。
- 询问或确认文件命名方式，例如 `实验名-班级-学号-姓名.docx`。
- 只把个人信息写入当前最终版报告和文件名，不沉淀到专属 skill。

## 10. 验证与交付

交付前检查：

- 原始文件未被修改。
- 输出文件存在且格式符合用户要求。
- 必要章节齐全。
- 未确认填写范围之外的内容保持原样。
- 环境、工具、版本、数据文件与用户确认一致。
- 封面个人信息和文件命名符合用户确认。
- 占位残留符合预期，最终版不应有草稿待办文字。
- 参考示例模式已在正文标注。
- 免责声明存在。
- DOCX 可打开，Markdown 结构清晰。

最后询问用户是否满意，并按 `custom-skill-policy.md` 处理专属科目 skill。
